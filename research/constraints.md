### 2.1.5 ⚠️ 致命约束：`file://` 单文件下读不到 LLM 响应

`vite-plugin-singlefile` 官方 README 明确列出（[官方文档]）：

> **What does work when running an HTML file locally** … Requests to external APIs (requires `{ mode: 'no-cors'}` in your `fetch` call)
> **What doesn't work** … Cookies (passed via HTTP headers, which don't exist for `file:///` URIs) … SPA routing via Web History API …

含义（Fetch 标准语义 [官方文档+标准]）：
- `file://` 下没有 HTTP 头 → **Cookie 不可用**；
- 跨源请求要工作必须 `mode: 'no-cors'` → 返回 **opaque response**，**JS 读不到响应体**；
- 因此：**既不能带鉴权，也不能读到返回的 JSON**。

→ **"打开 HTML 就能调用大模型生成关卡"这个设计在离线单文件形态下不成立。** 除非评委是在 http(s) 服务器上打开你的文件（比赛只说"上传 H5 文件"，未说明托管方式）[官方文档：提交材料仅"H5 文件"]。
→ **处置：按最坏情况（双击本地打开）设计，全部预生成；如果一定要展示 AI 能力，把它放进「迭代优化过程文档」而不是游戏运行时。** 这同时也满足 20% 的迭代分。

### 2.2.2 ⚠️ 该插件的**官方文档化限制**（逐字，来自 README，都是翻车点）

- 插件的定位："This Vite build plugin allows you to _inline_ **all JavaScript and CSS** resources directly into the final `dist/index.html`" → **只保证 JS+CSS 内联**。图片/字体/音频**不自动内联**，需要自己抬 `build.assetsInlineLimit`。
- 作者自我否定："Bundling your _entire_ site into one file **isn't recommended for most situations**. In particular, this is **not a good idea, performance-wise**, for hosting a site on a normal web server."
- 单入口硬限制："**This is a _single file_ plugin. As in, it creates _one HTML file_ and _no other files_.** … either _will not work_ or _will not be optimized for_ apps that require multiple 'entry points' … see issue #51 … Issues opened requesting multiple entry points will be closed as `wontfix`."
- `file://` 下**不工作**：SPA routing via Web History API、Cookies、WebXR Immersive Mode、Worklets、Sourcemaps。
- 动态分包会坏："If your app still ends up with non-inlined chunks (_e.g._, from dynamic `import()` or lazy-loaded routes) that fail under `file://`, a different plugin may be a better fit. See issue #121."
- `file://` 下**可用**：`localStorage`、Persistent Storage API、FileSystem API、同目录相对文件请求、外站图片/字体、外站 API（需 `no-cors`）、SPA hash 路由、WebXR。

→ **设计含义**：**禁止 `import()` 动态分包 / 懒加载路由**（会破坏单文件）；**禁止依赖 Web History 路由**（用 hash 路由）；**不要把 localStorage 当唯一存档**（无痕/隐私模式下可能被清）。

### 2.2.3 手机浏览器首屏体积与性能上限（有来源的阈值）

**Web Almanac 2024（HTTP Archive）第16章 Page Weight，逐字** [官方文档]：

> The chart shows page weight growing over time, from **1,208 KB on desktop, 505 KB on mobile on Oct 2014**, to **2,652 KB on desktop, 2,311 KB on mobile Oct 2024**.

→ **可执行阈值：单文件 H5 游戏目标 ≤ 2.3 MB（= 2024年10月移动端中位页面重量）**。超过这个数，你就比"一半的网页"还重，而你还是个要被评委**当场打开**的游戏。

同章另一句（逐字）值得贴在墙上：
> …(1 MB) can actually feel slower than a page with one large 2 MB image because of the transmission overhead of 50 separate requests. … On mobile 4G/5G, signal interference can cause "packet loss."

→ 对单文件反而是**好消息**：1 个请求比 50 个请求好。所以**把 50 关做成纯数据（不新增图片/音频资源）是最优路径**。

**内联的代价**（算术 + 结构）[推测，但 base64 部分为确定算术]：
- base64 编码使二进制体积膨胀 **4/3 ≈ +33.3%**。
- 单文件牺牲 HTTP 缓存/增量更新：改一个字就要重下整个包。
- 牺牲代码分割与懒加载：**首屏必须等全部内容下载完**（因为你不能 `import()`）。
- 内联后 HTML 是一整块，**浏览器要在下载完才开始解析**（无 streaming 收益）。

**⚠️ 直接冲突**：题目要求 **50 关**，而"50 关要有体验变化"（30% 分值：`关卡与关卡之间有没有变化、节奏、惊喜、难度曲线`）。如果靠**新图片/新音频**来制造变化，base64 +33% 会迅速冲破 2.3 MB。
→ **必须用"规则变化 / 配色变化 / 数字变化"来制造 50 关的差异，而不是新美术资源。** 这也正好符合原文"不需要复杂美术（简洁风格反而是主流）"。

**拿不到的**：`web.dev` 的 **LCP 2.5s 阈值**（`https://web.dev/articles/lcp` 连接超时，WinError 10060，重试失败）→ 该具体阈值 [未验证]，不要引用为出处。

## 2.3 纯 H5 vs 微信小游戏 / 抖音小游戏

**结论：比赛只要求 H5，不需要额外适配。** [官方文档]

逐字证据（`block_sequence` #46、#56）：
> 用AI完成从创意到成品的全过程，**制作H5版本**
> …包含以下内容：**最终游戏作品（H5 文件）**

小游戏/小程序**只在"赛题-调研"里出现**（#44）：
> 体验各大平台的轻度休闲游戏（Google Play / App Store / **微信小游戏** / **抖音小游戏**榜单）

→ **它们是"已验证玩法"的取材来源，不是交付平台。** 任何把工期花在微信小游戏/抖音小游戏移植、开放平台账号、审核、平台 SDK 上的计划都是**范围蔓延**。30% 的分数在关卡体验，20% 在迭代留痕——移植一分不得。

**差异点（结构性结论）** [官方文档（H5 侧）] / [未验证（小游戏侧数字）]：
- **交付形态**：比赛要"最终游戏作品（H5 文件）"——一个文件。小游戏要求提交代码包走平台审核，与"H5 文件"不是同一种交付物。
- **鉴权与 API**：小游戏有平台登录/支付/分享/广告 API 与后台；H5 没有。用不到，也不该用。
- **包体与审核**：小游戏有包体上限和多级审核；H5 无审核、无包体上限（但也无平台流量）。
- ⚠️ **我拿不到小游戏官方包体上限的确切数字**：`developers.weixin.qq.com` 与 `developer.open-douyin.com` 的文档正文**全部是前端渲染，纯 HTTP 抓取只能拿到导航壳**（实测：微信小游戏文档页 110 KB 里正文长度仅 5.4 KB；抖音小游戏页 935 KB 里正文长度仅 89 字符）。我试了 9 个候选 URL（含 `subpackages`、`code-split`、`network`、小程序分包页），**均未取到"主包/分包大小上限"的官方原文** → **该数字 [未验证]，不要写进方案。** 反正也不需要：比赛不要小游戏。

## 2.3.1 结论

**不要做小游戏适配。** 若将来想加分，可在「设计思路文档」里写一段"若移植小游戏会如何调整"，零成本拿到叙事分，但不写一行移植代码。

## 2.4 50 关批量生成 + 求解校验 + 难度分级的计算成本

**方法**：本机 bundled CPython 单线程，自主实现生成器 + 求解器，每品类 50 关。脚本 `.scratch/bench_levelgen2.py`、`.scratch/bench_levelgen3.py`、`.scratch/bench_ms2.py`，日志 `bench_out2.txt`/`bench_out3.txt`/`bench_ms2.txt`。**证据等级：全部 [实测]。**

### ⚠️ 先自我纠错（核验者的自我泼冷水）

第一版基准（`bench_levelgen.py`）有 **两个 bug**，产出的数字**作废**，不得引用：
1. **推箱子生成器的 pull 候选过滤条件写反了**（只允许玩家退到墙里），导致 35/50 关卡"不可解"——那是 bug，不是发现。修正后 **49/50 关卡被 A\* 证明可解，0 个不可解**。
2. **扫雷的零格没有 flood-fill**，导致"无猜可解率"被严重低估为 **0.2%**。修正后是 **57.12%**——**差 285 倍**。若照抄 v1 数字，会得出"随机扫雷几乎无法生成无猜关卡、要 500 次拒绝"的错误结论。

### A) 数独（生成 + 唯一解证明 + 技巧分级）

| 指标 | 实测值 |
|---|---|
| 50 关 生成+唯一解证明+分级 总耗时 | **7.45 s** |
| 单关生成 mean / p50 / p95 / max | **136 / 113 / 304 / 778 ms** |
| 单关难度分级（naked+hidden singles）mean / p95 | **12.5 / 24.8 ms** |
| 给定线索数 | 27–31 |
| 仅靠 naked+hidden singles 可解 | 38/50 |
| 外推 500 关 / 5000 关 | ~74 s / ~12.4 min |

> 唯一解证明是主要成本（搜索节点 mean 140、max 479）。**生成器本身（不做唯一解校验）快 10–20 倍。**

### B) 推箱子（逆向生成 + A\* 可解性证明）

50 关（7×7、2 箱、目标 25 次拉动）：

| 指标 | 实测值 |
|---|---|
| 可用关卡 | **49/50** |
| A\* 证明可解 / 证明不可解 / 撞状态上限 | **49 / 0 / 0** |
| 总耗时 | **0.18 s** |
| 生成 mean / p95 | **0.9 / 1.8 ms** |
| A\* 校验 mean / p95 | **3 / 11 ms** |
| 最小推动步数（难度代理） | 3–19，mean 10.5 |

**A\* 求解成本随箱子数爆炸**（8×8 房间，上限 400k 状态 / 20 s）— **这是本任务最有价值的"会翻车"实测**：

| 箱子数 | A\* 平均 | A\* 最大 | 平均展开状态 | 撞上限 |
|---|---|---|---|---|
| 2 | 0.007 s | 0.035 s | 1,124 | 0/8 |
| 3 | 0.045 s | 0.180 s | 4,366 | 0/8 |
| 4 | 0.220 s | 0.573 s | 16,567 | 0/8 |
| **5** | **4.401 s** | **12.598 s** | 178,049 | **2/8** |

→ **箱子数 4→5，校验成本涨 20 倍，并且开始撞上限（无法判定）。** 设计含义：**不要设计需要"证明可解"的重型推箱子/物流类谜题**。用反向生成 + 只校验"最小推动步数 ≥ 阈值"（如 ≥ 8 步）来筛难度，比完整 A\* 证明便宜得多。

### C) 扫雷（随机生成 + 无猜逻辑可解性）

**修正后（flood-fill 已修）**，生成 4000 张随机盘：

| 盘面 | 无猜可解率 | 每张耗时 | 每个可用关卡的拒绝数 |
|---|---|---|---|
| 8×8 / 6 雷 | **92.22%** | 0.63 ms | 0.1 |
| 8×8 / 8 雷 | **78.75%** | 1.41 ms | 0.3 |
| 8×8 / 10 雷 | **57.12%** | 1.66 ms | 0.8 |
| 8×8 / 12 雷 | **31.82%** | 1.49 ms | 2.1 |
| 9×9 / 10 雷 | **80.88%** | 2.21 ms | 0.2 |
| 9×9 / 12 雷 | **64.92%** | 1.61 ms | 0.5 |
| 9×9 / 15 雷 | **32.05%** | 1.56 ms | 2.1 |

**生产run**：要凑 50 张 8×8/10 雷的无猜关卡，只需试 **91 张盘、0.11 秒**。

**诚实声明**：这个求解器是**可靠的（sound）但不完备（incomplete）**——只用"单点约束传播 + 子集规则 + 零格 flood-fill"，不用 1-2-1 模式或完全枚举。它**不会把有猜的盘误判为可解**，但**可能把本可无猜解出的盘判为需猜**。→ **上表数字是真实无猜率的"下界"，真值只会更高。** 别把它读成"随机扫雷很难生成"。

### D) 合计与结论

| | 50 关总耗时 |
|---|---|
| 数独（生成+唯一解+分级） | 7.45 s |
| 推箱子（生成+A\* 证明） | 0.18 s |
| 扫雷（生成+无猜校验） | <0.2 s |
| **合计（三种品类都做）** | **≈ 7.7 s 本地 CPU** |

→ **50 关的"生成 + 求解校验 + 难度分级"是秒级本地计算，完全不是瓶颈。** 瓶颈是：
1. 50% 权重的**玩法规则设计**（"规则是否巧妙，是否让人有'再来一局'的冲动"）——**生成器帮不了你**；
2. 30% 权重的**难度曲线/节奏/惊喜**——需要人玩、人调，不是靠公式；
3. 20% 权重的**迭代留痕**——需要从第一天记录。

⚠️ 另一个隐忧：**"AI 批量生成关卡"很容易生成 50 关同质关卡**（同参数不同种子）。评委看的是"变化、节奏、惊喜"（30%）。**必须人工定义每 5–10 关一个新机制**，并把它写进关卡数据。

### 2.5.4 判断：哪些方向已被做烂，哪些不是

**被做烂（高风险，除非有决定性微创新）**：
- 纯粹的数独 / 扫雷 / 俄罗斯方块 / 2048 / Flappy / 贪吃蛇 / Wordle **1:1 克隆**（均为 5 万–11 万仓库级）。
- "AI 帮你解这个经典谜题"（AI_Sudoku、DeepLearningFlappyBird 类）。
- "LLM 当对手/当 NPC"（wolfcha、Microverse 类）。
- "经典 IP 的 H5 复刻"。

**不是"被做烂"，但需要警惕的另一面**：
- ⚠️ **主办方自己的口味恰恰是"经典融合"**：Meowdoku = 数独×扫雷；Vita Mahjong = 麻将消除；Amaze Go! = 箭头解谜；Tile Explorer = 堆叠消除（类"羊了个羊"）。他们明确把 **合成大西瓜** 当成"微创新"的教学范式。
- → 所以**真正的风险不是"用了经典玩法"，而是"没有那个融合/规则扭转，只剩克隆"**。原文自己给了判据：**"没有任何一个元素是新的，新的是它们碰撞后产生的化学反应。"**
- → 建议的差异化落点是**两个成熟机制的融合**（这是 50% 权重"玩法设计"的直接得分点），而**不是**去发明全新品类（`topic:ai-game` 里那些全新品类作品星数并不高，且原文说"规则越简单越难做好"）。

### 2.5.5 ⚠️ 知识产权：克隆路线的无保护风险

**官方文档里完全没有原创/版权/知识产权条款**（见 1.3 缺口表，[实测]）。这意味着：
- 你**既没有**"原创声明要求"的明确指引，**也没有**"可以自由改写经典玩法"的安全港。
- 玩法规则本身通常不受著作权保护，但**具体美术、音乐、名称、代码、UI 布局**受保护。
- 风险动作：使用"羊了个羊""合成大西瓜"的**原始美术/音效/名称**；把开源仓库代码整段搬进作品。
- **处置（低成本、必须做）**：全部使用自制/AI 生成且**可商用许可明确**的素材；不复用任何商业游戏的美术与名称；在「设计思路文档」里明确写"规则为自研融合，素材来源与许可如下"。**因为没有官方条款，这份自证清单是唯一的保护。**
